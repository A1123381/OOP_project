# 專案工作說明：Exam Battle 考試題庫與多人競賽練習系統

## 1. 專案目標

開發一套類似 Kahoot 的多人考試練習系統，讓使用者可以匯入歷屆考試試題，將紙本或 PDF 考卷轉換成數位題庫，並透過單人練習或多人即時競賽的方式進行考試練習。

本系統的核心概念是：

**匯入考卷 → OCR 辨識 → 人工校正 → 建立題庫 → 單人練習／多人競賽 → 成績統計 → 錯題複習。**

系統不限定任何科目。使用者可以匯入任何類型的考卷，例如資訊、數學、英文、歷史、自然科學、證照考試及其他學科。

## 2. 重要開發限制

目前專案暫時不使用任何 AI 功能。

請遵守以下限制：

1. 不整合 ChatGPT、Gemini、Claude 或其他 LLM API。
2. 不使用 AI 自動生成題目。
3. 不使用 AI 自動判斷答案。
4. 題目來源以使用者提供的歷屆考卷為主。
5. 可以使用 OCR 技術辨識考卷文字，但 OCR 不等於 AI 題目生成。
6. OCR 辨識結果必須提供人工檢查及修改功能。
7. 系統必須具有通用性，不可將科目或題目內容寫死在程式中。

## 3. 核心功能需求

### 3.1 使用者系統

- 使用者註冊及登入。
- 使用者個人資料管理。
- 顯示個人考試紀錄。
- 顯示個人答題統計。
- 管理個人錯題。

### 3.2 考卷匯入系統

支援使用者匯入以下格式：

- PDF
- JPG
- JPEG
- PNG

匯入後，系統應該：

1. 讀取 PDF 或圖片。
2. 如果是 PDF，將頁面轉換成圖片或直接擷取可讀取的文字。
3. 使用 OCR 辨識考卷文字。
4. 嘗試將文字整理成題目及選項。
5. 將辨識結果顯示給使用者。
6. 允許使用者修改題目、選項及答案。
7. 確認後將題目儲存至資料庫。

注意：OCR 可能無法正確辨識題目編號、選項、數學公式、表格、圖片或程式碼，因此必須保留人工校正流程。

### 3.3 題庫管理系統

題庫不限定科目，應由使用者自行建立分類。

每份考卷至少應包含：

- 考卷名稱
- 科目或分類
- 考試年份
- 考試類型
- 題目清單
- 建立者
- 建立時間

每道題目應包含：

- 題目內容
- 題目類型
- 選項
- 正確答案
- 詳細解說（選填）
- 所屬考卷
- 題目圖片（選填）
- 題目順序

支援題型：

- 單選題
- 多選題
- 是非題
- 填充題
- 簡答題
- 問答題

題庫管理需要考慮：

- 公開題庫
- 個人私人題庫
- 題庫搜尋
- 題庫分類
- 題目新增、修改及刪除
- 題目重複使用

### 3.4 答案管理系統

正確答案可以透過兩種方式建立：

1. 使用者手動輸入答案。
2. 匯入答案卷，再透過 OCR 辨識。

答案卷辨識後也必須允許人工修改。

系統不得自行推測無法確認的正確答案。

### 3.5 單人練習模式

使用者可以選擇：

- 完整考卷練習。
- 隨機抽題練習。
- 指定科目練習。
- 指定題庫練習。
- 錯題複習。

答題結束後顯示：

- 總分
- 答對題數
- 答錯題數
- 正確率
- 每題正確答案
- 作答時間
- 錯題清單

### 3.6 多人即時競賽模式

系統需要支援多人同時進入同一個考試房間。

主要流程：

1. 使用者建立競賽房間。
2. 系統產生房間代碼。
3. 其他使用者輸入代碼加入。
4. 房間建立者可以開始遊戲。
5. 所有玩家同步收到題目。
6. 玩家在時間限制內提交答案。
7. 伺服器統一判斷答案及計算分數。
8. 每題結束後同步顯示排名。
9. 所有題目完成後顯示最終排行榜。

需要實作：

- 建立房間
- 加入房間
- 離開房間
- 玩家列表
- 房間代碼
- 開始及結束遊戲
- 題目同步
- 倒數計時
- 答案提交
- 即時分數計算
- 即時排行榜

重要規則：

計時、答案判斷、分數計算及排行榜必須由伺服器負責，不能讓客戶端自行決定，以避免作弊及資料不同步。

### 3.7 錯題與成績管理

系統應記錄每位使用者的：

- 考試紀錄
- 每題作答答案
- 正確或錯誤狀態
- 作答時間
- 考試分數
- 錯題清單

使用者可以查看過去答錯的題目，並重新練習。

## 4. 技術架構

如果使用 Java 開發，建議採用以下技術：

| 項目 | 建議技術 |
|---|---|
| 程式語言 | Java |
| 使用者介面 | JavaFX或是swing |
| 多人即時通訊 | Java Socket |
| 資料庫 | MySQL |
| 資料庫連線 | JDBC |
| PDF 處理 | Apache PDFBox |
| OCR | Tesseract OCR |
| Java OCR 整合 | Tess4J |
| 資料傳輸格式 | JSON |

如果未來決定開發成網頁版，應考慮將 Java Socket 改成 WebSocket，並重新規劃前後端架構。

## 6. 資料庫設計方向

建議至少建立以下資料表：

### users
儲存使用者帳號及個人資料。

### subjects
儲存科目及分類。

### exams
儲存考卷基本資料。

### questions
儲存題目內容及正確答案。

### question_options
儲存選擇題的選項。

### rooms
儲存競賽房間資料。

### room_players
儲存房間內的玩家。

### game_records
儲存每場競賽的成績。

### answer_records
儲存每位使用者的答題紀錄。

### wrong_questions
儲存使用者的錯題資料。

資料庫設計應避免將題目直接寫死在程式中。

考卷與題目應分開管理，一份考卷可以包含多道題目，同一道題目也應考慮未來在不同練習或競賽中重複使用的可能性。

## 7. 開發優先順序

請按照以下順序逐步開發，不要一次實作所有功能。

**第一階段：基本通訊**
- 建立 Java Socket Server。
- 建立 Client。
- 測試多個 Client 同時連線。
- 實作基本訊息傳送。

**第二階段：使用者及房間**
- 使用者登入。
- 建立競賽房間。
- 加入競賽房間。
- 顯示房間玩家。

**第三階段：基本題庫**
- 建立資料庫。
- 手動新增考卷。
- 手動新增題目。
- 管理題目及答案。

**第四階段：多人競賽**
- 同步題目。
- 倒數計時。
- 提交答案。
- 計算分數。
- 即時排行榜。

**第五階段：個人紀錄**
- 儲存考試紀錄。
- 顯示個人成績。
- 建立錯題本。
- 支援錯題複習。

**第六階段：考卷匯入**
- 支援 PDF 上傳。
- 支援圖片上傳。
- PDF 文字擷取。
- 圖片 OCR 辨識。

**第七階段：OCR 校正**
- 顯示 OCR 辨識結果。
- 編輯題目內容。
- 編輯選項。
- 設定正確答案。
- 確認後匯入題庫。

**第八階段：系統完善**
- 公開及私人題庫。
- 題庫搜尋及分類。
- 完善操作介面。
- 測試多人同時競賽的穩定性。
- 處理例外及錯誤訊息。

## 8. AI Agent 的工作規則

在協助開發本專案時，請遵守以下原則：

1. 先理解整體架構，再開始撰寫程式碼。
2. 不要擅自刪除或更改已經確定的功能需求。
3. 不要自行加入 AI 題目生成或 LLM API。
4. 不要把系統限制在資訊工程或任何單一科目。
5. 所有題目內容都應該由使用者匯入或手動建立。
6. OCR 結果必須允許人工校正。
7. 程式碼應保持模組化，避免將所有功能寫在同一個類別。
8. 資料庫操作應使用 DAO 或其他適當的資料存取層。
9. 多人競賽的關鍵邏輯必須由伺服器控制。
10. 每次開發應先說明修改內容、涉及的檔案及實作方式。
11. 如果需要修改既有程式碼，應先理解原本程式架構，避免破壞已完成的功能。
12. 每個階段完成後，提供測試方法及預期結果。
13. 遇到需求不明確時，先提出問題，不要自行假設重要規格。
14. 不要只提供概念或偽程式碼；在要求實作時，應提供可整合、可執行的完整程式碼。

## 9. 目前尚待確認的規格

以下項目尚未正式決定，開發前需要確認：

- 題庫是否同時支援公開題庫及私人題庫。
- 答案是否同時支援答案卷 OCR 匯入及手動輸入。
- 練習模式是否同時支援完整考卷及隨機抽題。
- 最終系統採用 JavaFX 桌面版或網頁版。
- 是否需要管理員及題庫審核機制。
- 多人房間是否需要房主權限及踢除玩家功能。

在這些規格確認前，請將它們視為待討論事項，不要直接當成已確定需求。

## 10. 第一個開發任務

請先不要直接開發完整系統。

第一步請完成以下工作：

1. 閱讀並分析整份專案需求。
2. 提出合理的系統架構。
3. 說明 Client、Server、Database 之間的關係。
4. 提出資料庫 ER Diagram。
5. 規劃第一階段的開發檔案。

7. 等待確認後，再開始撰寫第一階段程式碼。

**專案最終目標：建立一套不限定科目、能夠將歷屆考卷轉換成數位題庫，並支援單人練習、多人即時競賽、成績統計及錯題複習的通用考試練習平台。**
